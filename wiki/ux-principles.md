# UX principles

How to decide what a screen should *be* — who it serves, what job it accomplishes, and how the layout earns its shape — before any component gets picked. This is the judgment layer beside your stack's UI/component conventions, which own the mechanics — which component, which token, which library — and live in [the code rule](../.agents/rules/code.md#where-things-go). Every UI-bearing change applies these principles in a `## UX` section of its design.md (see [the change loop](development/the-change-loop.md)); the section template is at the [bottom of this page](#the--ux-section-in-designmd). The screen itself is sketched as a picture on [the change's review page](#the-review-file), which every change carries, so the layout is argued from a picture rather than a paragraph. When the real thing is cheap to build, build it: a [mini app](stack/mini-apps.md) preview shows the actual screen.

**It applies only to changes that add or restructure a user-facing screen.**

The one-line version: **UX leads, visuals serve.** First get the job and the flow right; then use hierarchy to make the screen express that flow. A beautiful screen that serves the wrong job is a failure; a plain screen that finishes the job in one straight line is a success.

## Start from the use case

Never start from a layout. Before drawing anything, answer the **UX brief**:

- **Who is here, and what job are they trying to accomplish?** Not the feature name — the actual job. Not "manage the listings page" but "copy our good content onto the stale listings without doing it one-by-one."
- **What does *done* look like?** The end state the user is trying to reach. The screen should drive toward it, not just display data near it.
- **Context of use.** Desk or floor? Phone, tablet, or desktop? Gloved hands with a scanner? Interrupted every two minutes? One app can span a writer at a desk and an operator at a station — same design system, very different screens. **When the answer is a phone, the phone layout is the design, not an afterthought:** sketch it first, at phone width; set options or a before-and-after side by side only where both fit. A screen that only works at 960px is not finished.
- **Common case vs edge case.** The common case gets the real estate and the straight-line flow; edge cases may cost an extra step or live in a menu. Never let a rare case complicate the frequent one.
- **Frequency assumptions, stated explicitly.** "Operators run this ~200×/day; admins open the settings ~1×/month." Write the assumption down so it can be challenged — until you have real usage data, these are judgment calls; once you do, cite event counts instead.

Then design the **flow**: the shortest path from intent to done for the common case. Smart defaults pre-filled from context, no dead-end states, no detour through a second screen the common case doesn't need. Only after the flow works do visuals enter.

## Principles

Distilled from [Refactoring UI](https://www.refactoringui.com/). A mature design system already solves the book's "define systems in advance" chapters — type scale, spacing scale, palette are decided; never invent values outside them. What's left is judgment:

- **Hierarchy is everything.** A screen where everything is equally loud says nothing. Decide what matters most for the job and make everything else visibly subordinate.
- **One primary action per screen.** The job's next step gets the one solid, filled button; everything else is secondary (outline) or tertiary (ghost/menu). Two primary buttons means the brief wasn't finished.
- **Emphasize by de-emphasizing.** Make the signal stand out by muting the noise — a muted color, lighter weight, smaller supporting text — rather than making the signal bigger and bolder.
- **Weight and color before size.** Hierarchy comes from font weight and semantic color far more than from font size. Reach for size last.
- **Labels are a last resort.** Format data so it explains itself: `3 boxes · 82 items` beats `Boxes: 3  Items: 82`. When a label is needed, combine it with the value or mute it — the value is the content.
- **Density is decided by the job, not by taste.** Start with generous white space and remove deliberately — except where density *is* the feature: an operator scanning a queue wants tight rows; a settings page wants air. The use-case brief decides which. You don't have to fill the screen — a narrow, focused column beats stretched content.
- **Unambiguous spacing.** More space *between* groups than *within* them, always — ambiguous gaps make readers guess what belongs together.
- **Design the empty state.** First-run and zero-results screens start the job (the primary action inline), never just announce absence.
- **Fewer borders.** Separate with spacing and a background shift, not boxes inside boxes. Borders are the last tool, not the first.
- **Never rely on color alone.** Pair color with an icon, label, or weight change — accessible contrast and dark-mode legibility are part of the mechanics [your UI conventions](../.agents/rules/code.md#where-things-go) own.
- **Close stands alone.** In a full-screen view or a pop-up, *Close* sits alone in its corner, and the other controls sit in a bar away from it. A switch beside *Close* hides the way out.
- **One deliberate touch per screen.** An accent border, a designed detail — polish is a spice, not a base.

## The `## UX` section in design.md

A change that adds or meaningfully restructures a screen or component, not merely touching a UI file, includes a `## UX` section in its design.md: [the drawing guide](../.agents/plugins/loop/skills/plan/references/drawings.md#the--ux-section-in-designmd) owns its shape. It records who the screen is for, the shortest path, the one primary action, and the parts reused.

Worker-only or UI-less changes skip the section entirely and draw no screen. They still get a review page, with one drawing that carries the change by default: a flow as a Mermaid picture, a file tree as text; other bullets stay text. Prefer mirroring the closest existing screen over inventing a new pattern — name which screen in the brief.

### The review file

The picture lives in the proposal and shows at `openspec/changes/<name>/review.html` — one page per change, built by [the plan skill's builder](../.agents/plugins/loop/skills/plan/scripts/build-review.mjs) from `proposal.md` and [the fixed kit](../.agents/plugins/loop/skills/plan/references/review-kit.html). The page follows [the review page standard](review-pages.md): its frame, OK and Note on each card, and notes are the same on every review page. A plan's page is Why, the What Changes items with their drawings, and the decisions, each labeled *asked* or *assumed*. It wears the app's look, light to start on every device, with a switch in the top right that turns it dark: [the shared look](stack/mini-apps.md#the-home-page-lists-the-apps) says how it gets there.

A drawing is a fence inside the bullet it explains, drawn by [the drawing guide](../.agents/plugins/loop/skills/plan/references/drawings.md). A flow (steps, a back-and-forth, states) is a `mermaid` fence, which the builder draws as an inline picture when it builds the page, so the page runs no diagram code and stays offline. A screen is a `screen` fence: HTML built from the app's own parts (card, buttons, text box, tag, gray placeholder bars) laid out in rows and columns, so it looks like the real screen, wraps its text, and follows the light and dark switch. Its controls do nothing when tapped; a tap places a note. Arrows, layers, or any other free drawing is an `svg` fence painted only in the page's named colors. The builder keeps only allowed parts and writes each picture out again itself; a script, style, link, or image inside a drawing stops the build. A picture file, such as a screenshot, is a `picture` fence: one `[label:] path` line per PNG, JPEG, or WebP file in the change's own folder, such as `Before: pictures/inbox.png`. The page carries each picture inside itself, so it opens with no internet, and gives each label its own picture in [the card's view](review-pages.md#the-card-view). A web address, or a path that leads out of the folder, stops the build. A picture over 150 KB warns. A picture over 300 KB, or a built page over 1.5 MB, stops the build, because the Inbox keeps at most 1.6 MB a page; a page over 800 KB warns, because it opens slowly on a phone. Take only the visible part at phone width. A table is a Markdown table, shown as a page table with a note on each row. A small listing such as a file tree stays a `text` fence, and so do drawings in chat, which shows no pictures. A Mermaid, screen, or SVG mistake stops the build with its item and proposal line, and the last good page stays. One drawing carries the change by default, in the pattern that fits what its bullet explains: steps, a back-and-forth, states, or a before-and-after of a changed flow or screen. What a screen sketch must hold follows from the rest of this page, and [the plan's review page rules](../.agents/plugins/loop/skills/plan/references/review-page.md#the-review-file) own it: every screen and state in the flow, *Before* beside *After*, real pictures from [the prototype](prototypes.md), one primary action, phone first when the brief says phone, and real words. A state a reviewer can not see is a state nobody designed.

Each drawing and picture shows at the start in its card's view, fitted to the view's width, and a drag still scrolls the page. A tap shows it full screen, where the reviewer pinches or presses + to zoom and drags to move it. How a reviewer notes, sends, and marks a card OK is in [the review page standard](review-pages.md#notes-on-words-and-spots). **Copy notes** produces notes on the plan to paste into chat — *notes on the plan from the review page, don't build yet* — with one bullet per note, by change number. **Save copies the same notes too**, with every saved note; a failed copy still keeps the note. Opened through [a reply link](development/reply-links.md), the button reads **Send notes** and sends them to the chat instead. A question gets its answer in chat and leaves the plan alone; a change updates the plan and rebuilds its page. Notes alone wait for a build choice. On a reply link, the footer shows **Send notes**, **Build it**, and **Build and publish**, with Send notes as its one primary action. Either build choice sends saved unsent notes and OKs together with the action; the chat updates the plan, answers questions without unrequested edits, and continues. Publish confirmation sits above the bar. Escape or an outside tap dismisses it. Sending and building pause together until acknowledgement. Only submitted, unchanged note content is marked sent after success; drafts and later edits stay unsent. Failures preserve notes, and a changed plan [asks for reload](development/reply-links.md#a-plans-link).

### The preview page

After a build that changes screens, `/apply` shows them on a preview page, not as pictures in chat ([finish with a preview](../.agents/plugins/loop/skills/apply/SKILL.md#finish-with-a-preview)). [`preview-review.mjs`](../.agents/plugins/loop/skills/apply/scripts/preview-review.mjs) copies each changed screen's pictures into the git-ignored `.scratch/<change>-preview/` folder, writes a short proposal there with one item per screen, *Live now* and *Preview* side by side (a new screen has *Preview* alone), or *Approved* and *Built* for a screen the plan showed from its prototype, and builds it with the same builder and kit as a plan page. Each screenshot is phone width and shows only the visible part (no `--full-page`). Add computer width only where the layout differs and the page stays under 800 KB. The page has no Decisions. Its title asks *Built: look, then publish?*, and its notes have their own line, *notes on the preview from its review page, don't publish yet*, so they never mix with the plan's notes. A reviewer taps a picture to see it full screen, then taps a spot to note it, such as *this button is too small*. On a reply link, the footer shows **Send notes** and **Publish** only: the build is done, so no build choice is left. **Publish** asks *Goes live, can't be undone* first, then asks the chat to publish. Notes go to the chat, which changes the build and makes a new preview page. Each footer button on any page shows only when its link offers it.
