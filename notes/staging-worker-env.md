# Staging as its own Cloudflare Worker

## Where this came from

The user hit it in **wongos** (a downstream repo that took the stack pack, Worker `wongos`, D1 `wong-db`): queue-driven recipe imports couldn't be tested on staging, and they suspected "two different databases on the same worker." They arrived with an analysis from another chat proposing Wrangler environments, and asked for it to be checked rather than taken on faith.

The other chat's conclusion was right; its diagnosis stopped one level short, and the level below is what set the scope.

## The actual constraint

Cloudflare Workers Builds **deploys** on the production branch and **uploads a version** on every other branch. The preview URL shape gives it away: `<branch-alias>-<worker>.workers.dev` is a version alias, not a Worker.

**A version only serves HTTP.** Queue consumers, cron triggers, DO alarms — every non-request entry point — are attached to the Worker's *deployed* version. So the old model (`swap-d1-id.js` rewriting `database_id` inside the uploaded version) isolated the request path and was structurally incapable of covering anything else. Not a partial fix: a fix for exactly one code path.

This is why "add a second queue" doesn't work — a consumer registers against a **Worker**, so a `*-staging` queue naming the same Worker still delivers to the production deployment.

## Decisions and what was ruled out

- **A Wrangler environment, not a runtime flag.** The bindings themselves must differ; gating on an env var at runtime leaves staging logic in production code paths forever.
- **`cf-deploy.sh` exists because Workers Builds has one deploy command for all branches.** That single fixed command is *also* why `swap-d1-id.js` existed in the first place — the swap was a workaround for not being able to say `--env staging`. The user confirmed the deploy command **is** configurable, which is what made the whole change viable. It was the gating unknown.
- **Per-commit preview URLs are generated by the default deploy command.** They're free today, so it reads as though they'd survive — they don't. Overriding the deploy command silently switches them off, so keeping them is now an explicit `wrangler versions upload --env staging --preview-alias <branch>` line. Both non-production commands need `--env staging`; dropping it from the upload silently reinstates the original bug.
- **Twin by default, never a namespace prefix.** The deciding asymmetry: a twin resource needs *zero* application code (the Worker never learns which one it got), a prefix needs every call site to cooperate forever and one omission writes into production data. The other chat suggested an R2 `staging/` key prefix; rejected on this basis — a second bucket is free.
- **Per-PR Worker environments: declined, and documented as declined** so it isn't re-litigated. Cloudflare gives a URL per version, not a Worker per PR (the Vercel/Netlify mental model doesn't transfer). Doing it by hand means per-PR D1 + queue + bucket + secrets + Access policy + teardown-on-close — a provisioner larger than the app.
- **Shared staging is not a regression.** The user pushed back on two branches overwriting each other. It's worth remembering the pack's staging *database* was already shared across all branches (one `preview_database_id`) and `d1-pipeline.md` already documented branches stomping each other. Code isolation now merely matches the isolation the data never had.

## Found while implementing

- **A twin staging D1 has its own `database_name`** — D1 names are unique per account, so `wong-db` and `wong-db-staging` can't share one. The name readers had to become environment-aware (read from inside the `env.staging` block), and to error explicitly rather than silently falling back to production's name. Not anticipated in the plan.
- **`scripts/lib-wrangler-config.sh` was extracted** rather than copy the config-discovery rule a third time (bash in `cf-build.sh`, bash in `cf-deploy.sh`, JS in `lib-wrangler-config.mjs`). A build and its deploy resolving *different* apps would fail silently and confusingly. This deviates from tasks.md, which said to leave `cf-build.sh`'s discovery alone; recorded as tasks 1.5/1.6.
- **The existing Access wildcard `*.<subdomain>.workers.dev` already covers the staging Worker** and its aliases — no new policy needed, contrary to the initial assumption. The runbook says "confirm" rather than "add."

## The rehearsal, and why it earned its keep

The user asked "how can we confirm that this works before we /ship?" — a good question, because at that point *nothing* had been executed against Cloudflare. Everything verified so far only proved the scripts did what was written, not that what was written matched Cloudflare's behaviour.

Rehearsed on the account's existing test D1s plus a scratch Worker and twin queues (all torn down after). It found a bug that no amount of local testing would have:

> **`wrangler versions upload --env staging` fails against a Worker that doesn't exist yet.** *"You cannot upload a new version of a Worker that does not yet exist. Please run the `deploy` command first."*

That is exactly the state on a repo's **first** branch push, and with the upload ordered first `set -e` killed the script before the deploy that would have created the staging Worker. Every adopting repo would have hit it on day one, and the error message points at a fix (`run deploy first`) that reads like a wrangler quirk rather than a bug in the pack — easy to misdiagnose. **Deploy first, upload the alias version second.**

The rehearsal then positively demonstrated the central claim: a message enqueued on the staging queue was handled by the *staging* Worker and written to the *staging* database, while the production database's only row came from the production Worker. Two distinct Workers, one consumer each, no cross-contamination.

The general lesson worth carrying: **for a payload change, the cost of a wrong assumption is multiplied by every repo that takes the pack**, and un-propagating it is manual. A ~15-minute rehearsal against real infra is cheap against that. The 2026-07-28 D1 pipeline test set the same precedent.

Two smaller findings:

- Wrangler **warns on a production deploy** when environments are defined but none is named. Harmless — the printed bindings are the top-level production ones. `--env=""` silences it and binds identically (verified by dry-run), but it's a newer wrangler semantic and the pack pins no wrangler version, so it was documented as expected rather than "fixed". A version-dependent flag is a worse failure mode than a cosmetic warning.
- **Teardown has a circular dependency**: a Worker can't be deleted while it's a queue consumer, and a queue can't be deleted while a Worker binds it. Break it by deleting the *consumer* first (`DELETE /queues/{id}/consumers/{consumer_id}`), then the Worker, then the queue. `wrangler delete` didn't handle it; the REST API did.

**Still unverified, and unverifiable from this repo:** that Workers Builds accepts `bash scripts/cf-deploy.sh` as its deploy command. That's a dashboard setting on a connected repo — only wongos can prove it, and it's the assumption the entire change rests on.

## Repo-specific things worth knowing

- **`.claude` is a symlink to `.agents`**, and `CLAUDE.md` to `AGENTS.md`. Payload files are one edit, not two — don't hunt for a second copy to keep in sync.
- **This repo's own `app/wrangler.jsonc` has no `d1_databases` binding at all.** It's the scaffold SPA. The pack's wrangler config lives in `.claude/skills/wong-sync/references/stack-pack-fragments.md` as a guided merge fragment, not as a real config in this repo — so there was nothing here to migrate.
- The scripts were exercised against a synthetic repo in `/tmp` (an `app/` layout with a prod + `env.staging` config) since this repo can't run them for real. Worth repeating for any future pack-script change — `bash -n` alone wouldn't have caught the database-name problem.
