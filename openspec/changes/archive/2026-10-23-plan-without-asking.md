# Ask for a change, get a plan to review

**Status:** ready-to-ship
**Branch:** seamless-nav-build
**Open questions:** none

## Why

Ask for a change without a command, and the assistant can stop at *Plan it?* before it writes anything. Once the plan is ready, it asks again with a card: *Build it now / Build and publish / Review the plan / Stop*. The plan's page already has *Build it* and *Build and publish* buttons, so the card repeats a choice the page owns, and the extra stop slows every change.

## What Changes

- **A request goes straight to a plan.** Ask for a change in plain words and the assistant thinks it through, asks only what it must, and writes the plan. It never stops at *Plan it?* and never says which step it is on. Typing `/explore` yourself still means "let's just think": that one asks *Plan it?* before writing anything.
  ```mermaid
  flowchart TD
    ask["You ask for a change"] --> q{"Only you can answer?"}
    q -- yes --> answer["It asks; you answer"] --> plan
    q -- no --> plan["It writes the plan"]
    plan --> link["Review the plan: link"]
    link --> page["Tap Build it or Build and publish"]
  ```
- **A finished plan ends with its link, never a card.** The reply sums up the plan in a few lines, gives the link, and tells you to review it. You build, or build and publish, from the page's buttons. When the page opens only from its file, with no buttons, you say *build it* or *build and publish* in the chat.
  | | Today | After |
  |---|---|---|
  | Before the plan | Can stop at *Plan it?* | Asks only what it must |
  | End of the reply | The link, then a four-choice card | The link and "review the plan" |
  | Next step | Pick on the card or the page | Tap on the page |

- **Questions and the plan flow into each other.** Ask in the chat for a change to a waiting plan, and the assistant asks only what your message opens, updates the plan, and gives the new link, with no restart and no announcement. A question gets an answer and leaves the plan as it is. Notes sent from the page work as they do today.
- **The morning chief of staff leaves plans to you.** It used to answer an agent's *Build it now* card on its own. Now a plan from an agent it watches waits under *Needs you* in your inbox, or as a link in the daily chat, until you tap *Build it*.

Non-goals: no change to the plan page, its buttons, or the inbox. A typed command keeps its reach: `/apply` still plans and builds without a stop, and `/ship` still runs the whole way.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `asking-the-user`: a finished plan's reply ends with its link and a review line, with no question; a request with no command goes straight to planning; a follow-up asking to change a waiting plan updates it without restarting.
- `change-loop`: a change asked with no verb stops at the plan's link, from whose page the person builds or builds and publishes, with no question.
- `daily-routine`: a watched agent stopped at a plan's link is the person's to answer; the chief never builds it.
- `mini-apps`: a new tool asked with no verb ends on the plan's link and review line.
- `repository-improvement`: an `/improve-code` run ends at the plan's link like any finished plan, with no card.
- `ux-wireframes`: pasted notes that update a plan end on its link and review line, not a build question.

# Design

## Context

See proposal.md for why. Today [`asking-the-user.md`](../../../.agents/skills/explore/references/asking-the-user.md#end-every-reply-with-the-next-step) ends a finished plan with a four-option card, and `AGENTS.md` lists `/explore → /plan` for a request with no verb, so an agent can run `/explore` standalone and stop at *Plan it?*. [`build-review.mjs`](../../../.agents/skills/plan/scripts/build-review.mjs) prints one next-step line (`When you're ready, type /apply to build it.`) that only the *Review the plan* reply copies. The daily chief's [*Pick* bucket](../../../.agents/skills/daily/references/chief.md#sort-each-stop) answers the *Build it now* card.

## Goals / Non-Goals

**Goals:** a no-verb request lands at a finished plan with no extra stop; a finished plan ends on its link plus a review line; the chief never builds a plan.

**Non-Goals:** no change to the page, its buttons, the reply link, or the inbox; no new hook that enforces the ending.

## Decisions

- **The builder prints the review line, two ways.** With a live link (the page has *Build it* and *Build and publish*): `Review the plan, then tap Build it or Build and publish on its page.` From the file (no buttons): `Review the plan. When you're ready, say "build it" or "build and publish".` The builder knows which one it printed, so the rule just copies the line. The alternative, one line for both, would tell a file reader to tap buttons that aren't there. Scheduled goals keep their `/schedule` line.
- **A finished plan's reply copies that line and asks nothing.** The same line closes the *Review the plan* answer, replacing the old `/apply` line. A reply that changed a plan but must still ask (a blocker, an open choice) keeps its card and the *Review the plan* fourth option, for hosts that hide text above a card.
- **No-verb requests start at `/plan`.** `AGENTS.md`'s verb rule and the change loop's *Just ask* say the agent starts at `/plan`, whose bounded `/explore` asks what it must. `/explore`'s *Standalone* means typed by the person.
- **A chat follow-up on a waiting plan is a plan update.** `/plan`'s Review notes section widens to cover a chat message about the waiting plan: a bounded explore pass for only what it opens, then edit, rebuild, print. Page notes keep skipping explore.
- **The chief treats a plan stop as the person's.** `chief.md` adds the rule beside *Never sort a planning stop*: a stop at a plan's link goes to no bucket; the plan's own inbox item (made by the reply link) already sits under *Needs you*; without an inbox, the chief prints `Needs you: <title> — plan to review` and the link. It adds no second inbox item.

## Risks / Trade-offs

- [A host hides text above where a card would be] → no card follows a finished plan now, so the link is the last thing shown.
- [An agent still adds the old card from habit] → the rule changes in every skill that names it; the old option names vanish from live text.
- [Skill text grows past the recorded budget] → offset with cuts in the same files; `measure-context.mjs --check` decides.

## MODIFIED Requirements

### Requirement: Every reply that returns control ends with the next step

A reply that hands control back SHALL end with the decision that moves the work on, asked in the choice format through the question tool, with the report and every link written as chat text above it. A link SHALL NOT appear inside the question tool's question or options, and SHALL NOT appear only in the agent's reasoning; an option may name a link shown above it. A handoff the invocation already authorized SHALL continue instead of asking. The only replies that end with no question are a finished plan's, which ends with its link and a line telling the person to review it, and the answers to *Review the plan* and *See the preview*.

#### Scenario: A stage finishes

- **WHEN** a skill finishes and a structured question tool is callable
- **THEN** the report is chat text, and the next steps are asked through the tool, recommended first

#### Scenario: The chain continues

- **WHEN** `/ship` moves from one of its stages to the next
- **THEN** it continues without a next-step question

#### Scenario: A link the person needs

- **WHEN** a reply gives the person a link, such as a pull request, a key link, or a private form, and ends with a question card
- **THEN** the full link is a line of chat text above the card, and neither the card's question nor its options holds the address

### Requirement: A changed plan's reply carries its link

A reply that creates a plan, or changes what it says or its checklist, SHALL show the full link to the plan's review page as its own chat line, never inside a question. When the plan is finished and waits on the person, the reply SHALL end with that link and a line telling the person to review it, building or publishing from the page, and SHALL ask no question. When the page opens without build choices, that line SHALL say how to build or publish from the chat. Any other closing question in a reply that changed a plan SHALL offer to review the plan; choosing it SHALL show the link again and start nothing. Record-keeping alone (status, branch, decision log) SHALL NOT count as a change, and the link SHALL NOT add a stop.

#### Scenario: A plan finishes

- **WHEN** `/plan` finishes and the plan waits on the person
- **THEN** the reply ends with the plan's link and a line to review it and build from its page, and no question card

#### Scenario: A plan built on the way

- **WHEN** `/apply` plans a change and goes on to build it
- **THEN** the reply shows the plan's link and the build continues without a stop

#### Scenario: A save that only records progress

- **WHEN** `/save` updates only the plan's status and decision log
- **THEN** its report prints no plan link and its question offers no review of the plan

## ADDED Requirements

### Requirement: A request goes straight to a plan

A request for a change to the repo's code or process, made with no verb, SHALL go straight into planning: the assistant SHALL ask only the material questions, then write the plan, and SHALL NOT stop at a *Plan it?* question or announce which step it is in. Only a person who typed `/explore` SHALL get the *Plan it?* question. A chat message that asks for a change to a plan waiting on the person SHALL update that plan, asking only what the message newly opens and keeping settled answers, then show the plan's new link; a message that asks a question SHALL be answered as review notes are, leaving the plan unchanged.

#### Scenario: A plain request

- **WHEN** a person asks "make the plan page show the build buttons sooner" with no verb
- **THEN** the assistant asks only what it must, writes the plan, and ends with its link, without asking whether to plan it

#### Scenario: A follow-up on a waiting plan

- **WHEN** a plan waits on the person and they write in the chat "also cover the phone layout"
- **THEN** the assistant asks only a question that message opens, updates the plan, and shows its new link, without repeating earlier questions

## MODIFIED Requirements

### Requirement: The chief sorts each stop into three buckets

Each time a watched agent stops or asks something, the chief SHALL decide one of three things: reply *keep going* when the agent reported progress and named its next step; pick the answer when the question has a clear best answer that is safe; or tell the person at once. A safe answer stays in the agent's own work and can be undone. An answer that sends or posts a message, pays, publishes, merges, deletes or overwrites data, accepts terms, or changes a business record SHALL never be given by the chief alone: it SHALL go on one approval list the person clears with a single answer. An agent stopped at a finished plan's link SHALL wait for the person: the chief SHALL NOT reply to it, build it, or publish it, and SHALL point the person to the plan. When unsure, the chief SHALL tell the person. Each thing the chief does alone SHALL show as one line in the daily chat.

#### Scenario: An agent names its next step

- **WHEN** a watched agent ends its turn with "Tests pass; next I'll update the wiki page"
- **THEN** the chief replies *keep going* and shows `Kept going: <title>` in the daily chat, without asking the person

#### Scenario: A safe recommended choice

- **WHEN** a watched agent asks "Run the tests now (Recommended) / Skip them"
- **THEN** the chief picks *Run the tests now* and shows the pick in the daily chat

#### Scenario: A finished plan

- **WHEN** a watched agent stops with its plan's link and a line to review it
- **THEN** the chief sends the agent nothing, and the plan waits for the person under *Needs you* in the inbox, or as its link in the daily chat when there is no inbox

#### Scenario: A risky recommended choice

- **WHEN** a watched agent asks whether to send a drafted email to a customer, with *Send it* recommended
- **THEN** the chief sends nothing, puts it on the approval list, and relays the person's answer

#### Scenario: No clear answer

- **WHEN** a watched agent asks which of two suppliers to order from, with no recommendation and nothing in its brief
- **THEN** the chief tells the person at once, with the agent's options, and a phone notification where the app sends one

## MODIFIED Requirements

### Requirement: One plan, then it stops

A normal invocation SHALL authorize selecting one improvement and writing its plan, and nothing more: `/improve-code` SHALL NOT build, publish, or change any file outside the plan. The run SHALL end at the plan's link the way any finished plan ends. - **WHEN** a person invokes `/improve-code` and one improvement is supported
- **THEN** they get a plan's link to review and build from, and no code has changed

#### Scenario: A scheduled run
- **WHEN** a routine runs `/improve-code` and one improvement is supported
- **THEN** a saved plan waits for the person, their next chat shows it, and nothing is built or published

## MODIFIED Requirements

### Requirement: Pasted notes update the plan and stop

Pasted notes sent alone SHALL update that change's artifacts with no question round, only for notes that ask for a change, and log what each such note changed or why it was declined; a note that asks a question SHALL be answered as `asking-the-user` requires, with no edit. The reply SHALL rebuild the page when anything changed and end with the plan's link and a line telling the person to review it, as `asking-the-user` requires for a finished plan. Notes alone SHALL build nothing; an explicit accompanying build choice SHALL authorize applying those notes and continuing directly to that action, and SHALL change nothing when the change is not in this checkout.

#### Scenario: Notes pasted

- **WHEN** a reviewer pastes notes asking for changes to a change
- **THEN** the proposal, design, specs, and tasks reflect them, and no task is implemented

#### Scenario: The change is not here

- **WHEN** the change is not in the current checkout
- **THEN** the reply says so, and nothing changes

// The light and dark switch outside the app: inlined in the review page's <head>, served to private pages as /theme.js.
// It applies the saved choice before paint, then adds the button; storage that is off still switches, unremembered.
(function () {
  var KEY = 'wongstack-theme';
  var SVG = 'http://www.w3.org/2000/svg';
  // lucide's moon and sun. The icon shows the look a tap switches to.
  var ICONS = {
    moon: [['path', { d: 'M12 3a6 6 0 0 0 9 9 9 9 0 1 1-9-9Z' }]],
    sun: [['circle', { cx: '12', cy: '12', r: '4' }]].concat(['M12 2v2', 'M12 20v2', 'm4.93 4.93 1.41 1.41', 'm17.66 17.66 1.41 1.41', 'M2 12h2', 'M20 12h2', 'm6.34 17.66-1.41 1.41', 'm19.07 4.93-1.41 1.41'].map(function (d) { return ['path', { d: d }]; })),
  };
  var root = document.documentElement;
  var saved = null;
  try { saved = localStorage.getItem(KEY); } catch (e) { saved = null; }
  root.classList.toggle('dark', saved === 'dark');

  function icon(name) {
    var svg = document.createElementNS(SVG, 'svg');
    var attrs = { viewBox: '0 0 24 24', fill: 'none', stroke: 'currentColor', 'stroke-width': '2', 'stroke-linecap': 'round', 'stroke-linejoin': 'round', 'aria-hidden': 'true' };
    Object.keys(attrs).forEach(function (k) { svg.setAttribute(k, attrs[k]); });
    ICONS[name].forEach(function (part) {
      var el = document.createElementNS(SVG, part[0]);
      Object.keys(part[1]).forEach(function (k) { el.setAttribute(k, part[1][k]); });
      svg.appendChild(el);
    });
    return svg;
  }

  function draw(button) {
    var dark = root.classList.contains('dark');
    button.setAttribute('aria-label', dark ? 'Switch to light' : 'Switch to dark');
    button.setAttribute('aria-pressed', dark ? 'true' : 'false');
    button.textContent = '';
    button.appendChild(icon(dark ? 'sun' : 'moon'));
  }

  function mount() {
    if (!document.body || document.querySelector('.theme-toggle')) return;
    var button = document.createElement('button');
    button.type = 'button';
    button.className = 'theme-toggle';
    draw(button);
    button.addEventListener('click', function () {
      var dark = !root.classList.contains('dark');
      root.classList.toggle('dark', dark);
      try { localStorage.setItem(KEY, dark ? 'dark' : 'light'); } catch (e) { /* switched, not remembered */ }
      draw(button);
    });
    var slot = document.querySelector('[data-theme-toggle]');
    if (slot) slot.appendChild(button);
    else document.body.insertBefore(button, document.body.firstChild);
  }

  if (document.readyState === 'loading') document.addEventListener('DOMContentLoaded', mount);
  else mount();
})();
</script>
