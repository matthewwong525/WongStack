Who / job: a developer who lands on the repository from a link or a search, and decides in under a minute whether WongStack solves a problem they have. Done: they copy the setup prompt, or they know why WongStack is not for them. Context: GitHub on a desktop browser, drawn first; the phone view (toggle View: Phone) keeps the same order and folds the comparison table into a list. Frequency: once per visitor.

  1. Badges come first, so a visitor sees that CI passes, the license, and the version before they read. The version badge reads VERSION.
  2. The problem comes before the product. Today the first line names the product ("an AI knowledge center"); a visitor who does not know that term cannot tell if it is for them.
  3. One screenshot of a review.html page, not a GIF. It shows the output a user gets, and any change can make a new one.
  4. The copy prompt stays the one primary action. Nothing else on the first screen competes with it.
  5. The comparison is short and names each other tool fairly. The final cell text is for the README draft to decide; review the rows, not the words.
  6. Requirements say why Cloudflare is required and link SECURITY.md, instead of offering a path without Cloudflare.
  7. "Fork first" replaces "clone this repo": a visitor cannot push to this repository, and a fork PR is the way to send a change back.
  8. Not drawn: the workflow table, "Where the knowledge lives", and "Learn more". The plan does not say if they stay, move to the wiki, or shrink. "A few terms" moves to the wiki.

GitHub repository settings: the value today → the value after. The agent shows each row to you, then applies it with gh. Nothing changes before you see it.

Security
  • Private vulnerability reporting: off → on the channel SECURITY.md names works 1
  • Secret scanning and push protection: off → on a pushed token is stopped
  • Dependabot alerts and security updates: off → on pairs with the new dependabot.yml
Ruleset on main
  • Required checks: none → Test and Payload checks "CI is the gate" is enforced 2
  • Force-push and deletion: allowed → blocked
  • Bypass: none → repository owner only prose saves go straight to main 3
Pull requests
  • Merge methods: merge, rebase, squash → squash only matches what /ship does
  • Delete head branch after merge: off → on
About
  • Description: "My harness for building a collaborative AI knowledge center" → a third-person line that states the problem search results quote it
  • Topics: none → ai-agents, claude-code, codex, openspec, cloudflare-workers, developer-workflow
  • Homepage: empty → a link, shown for your approval value set when the agent shows it
Environments
  • production: none → deploys from main only a branch cannot deploy to production 4
  1. Today SECURITY.md points to a reporting form that is turned off. Turning it on makes the file true; the file does not change.
  2. The check names match the workflow names in .github/workflows/. A check that is renamed later must also be renamed here, or every PR waits for a check that never runs.
  3. Without an owner bypass, a wiki-only /save cannot push to main. The bypass is for the owner only; other people still go through a PR.
  4. The deploy workflow names the production environment, so the limit to main is enforced by GitHub, not only by the workflow's own branch filter.
