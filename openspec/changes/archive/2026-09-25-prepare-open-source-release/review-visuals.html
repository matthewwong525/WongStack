Where each Cloudflare token lives: after this change, and today.

After

User token, on the host only Changed 1

It stays in the primary worktree's .env. It mints the other two tokens.

Details

You create it with two permissions: User ▸ API Tokens ▸ Edit and Account ▸ API Tokens ▸ Edit. Set Account Resources to Include ▸ your account. Setup grants itself only the permission groups that each step needs. Setup reports each group that it granted. You can narrow the token back to the two permissions after setup. .env.example, the README, and the credentials page say this.

↓ Mints two tokens

<repo>-memory Kept

Goes to .env on the host.

Details

Actor: setup. Action: mint the narrow memory token and write it to .env. Result: the memory scripts read and write the store. CI never gets this token. This change does not change it.

<repo>-deploy New 2

Account-owned. It can deploy and nothing more.

Details

Actor: setup. Action: mint it with POST /accounts/{account_id}/tokens. Permissions: Workers Scripts Write, D1 Write, and Account Settings Read. Setup adds Workers R2 Storage Write only when the app's config binds a bucket. Result: a token that belongs to the account, so it outlives one person's user token. On a later run, setup reuses the token and rolls its value only when the secret is missing.

↓ Only the deploy token continues, through a pipe

gh secret set CLOUDFLARE_API_TOKEN Changed 3

The value goes straight to GitHub. No file gets it.

Details

Actor: setup. Action: pipe the minted value into gh secret set. Result: the secret holds the deploy token. The value is never written to disk, a note, or a log. The secret keeps its name, because wrangler reads that name natively.

↓

deploy.yml and wrangler deploy Kept

Production, staging, and the preview alias use the deploy token.

Details

Actor: CI. Action: run cf-deploy.sh with the secret. Result: the same three deploy paths as today. A workflow that reads the secret can deploy code, but it cannot mint tokens or take over the account. Contract tests run cf-deploy.sh against a fake wrangler. One live run from the host confirms that the permission list is enough.

Each Actions workflow can read it Removed

Risk: a workflow can take over the Cloudflare account.

Details

Actor: any workflow in the repo. Action: read the secret. Result: it can mint a new token with any permission. Installed repos should roll their user token after they sync.

  1. The user token starts with two permissions. Setup widens it only for each step, and it reports what it granted. Thus you can see the token's power and narrow it again.
  2. The deploy token belongs to the account, not to a person. When the person who ran setup leaves, CI still deploys. The permission list is the smallest set that deploys the Worker and migrates D1. The live smoke run confirms it.
  3. A pipe from the mint call to gh secret set keeps the value off the disk. The secret name does not change, so deploy.yml stays the same.
