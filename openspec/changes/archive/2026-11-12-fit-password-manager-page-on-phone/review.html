Why

On a phone, the live view of the password manager's own page (1Password) shows only a narrow strip at its left. The page stays as wide as the computer's screen, so the sign-in form sits off to the right, out of view. A person who opens the view to sign in to 1Password sees an empty corner and can't reach the form.

What Changes

  1. 1
    On a phone, the password manager's page narrows to fit, as a website already does. The whole sign-in form shows, with its button. The pictures are what a phone shows, taken from the agent's real browser with a stand-in sign-in page.
  2. 2
    A laptop sees no change. A wide view still shows the page at the screen's width.
  3. 3
    The site gets its own size back, as today. When you leave the password manager's page for the site, or the view ends, the site's page returns to the size it had.
  4. 4
    A first fix was tried and dropped. It made the browser's window narrow but left the page inside it wide, so the form stayed cut off. The tests showed that the browser does narrow the page when asked; it only never says that it did.

Non-goals: how the password manager is added or signed in to (the other part of this request); a change to how a website fits; the last few pixels of the toolbar's right edge on a phone, which a website loses the same way today.

What the build needs

  1. Ready 1Password in the agent's browser: it is added on this computer. The build opens a live view over its page at a phone's width; when it is done, one look on your iPhone is welcome but not needed.

Decisions

  1. assumed2026-11-12

    Assumed: drop the first try at a fix (size the browser's window with xdotool), because on the real browser the window narrowed to 500 px but the add-on page inside stayed 1920 px wide, and the form stayed cut off.

  2. assumed2026-11-12

    Assumed: narrow the page through the driver's own resize, sent without waiting, because on the real browser that resize changed the add-on page to 480 px and back to 1200 px; only its answer never came, and the driver worked again once back on the site.

  3. assumed2026-11-12

    Assumed: keep the page's height on the add-on page as the browser server set it (the screen less the browser's bar), because the view reads no bar there and would ask for the screen's full height, which would push the page's bottom off the screen.

  4. assumed2026-11-12

    Assumed: send a size to the add-on page only when it differs from the last one sent there, because the view asks again each minute, and each send leaves one answer waiting.

  5. assumed2026-11-12

    Assumed: not opening the add-on page in a fresh tab, which also fits, because that changes how the agent opens it (the other part's code) and still stops at 500 px.
