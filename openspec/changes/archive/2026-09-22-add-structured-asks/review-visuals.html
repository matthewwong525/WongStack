The clarification budget: the 80/20 test, small groups of questions, one exit round, four questions at most. It governs what to ask before planning, not what an ask looks like. A runbook cites the format without inheriting any of this.

Scope: the convention is one shared reference that every asking skill links. Each skill keeps only the specifics of its own question — the options and what each one costs.

  1. The recommendation is written into the option text, not carried by the tool. Any host that can show options can show it, and the reader sees the advice next to the cost of taking it.
  2. Free text stays open through whatever the host already gives the user — never a third "Other" option, which would be a duplicate of the reply box and a decoy choice.
  3. Keeping the budget out is the point of the split. Without it, /ship citing the format would inherit "at most four questions before planning", which does not describe a fix-or-merge fork.

What moves: the order itself

Today this list lives inside /explore's SKILL.md, written for the explore-to-plan transition, and /continue restates it in a bullet of its own. After this change it lives once in the shared reference, and every skill that asks — /ship, /verify, /apply, /continue, /improve, /wong-cloudflare and the rest — cites it there. /explore links down to it like everyone else.

Contract: the skill owns the question; the host owns the widget. The decision procedure is not new — what changes is that it stops being /explore's private text and becomes the one place every skill cites.

  1. The order is by callability, not by preference or by which host you think you are on. The first path that can actually run is the one taken.
  2. The failure worth naming: treating elapsed time or a highlighted default as consent. An unanswered question blocks; it does not quietly resolve itself.
  3. The only mechanism path that proceeds unanswered, and it pays for it with a visible assumed label on every option it took. (A skill may still record an assumption for other reasons — for example /explore running out of its question budget — but that is a budget decision, not a mechanism one.)

Nobody has to invent the next verb Changed

Either the work continues on its own, or the decision that restarts it is on screen.

Details

Actor: the user. Action: pick an option, answer freely, or let the chain run. Result: the thread never ends on a dead stop.

Where it applies: every stop that hands control back — a finished plan, a blocked task, a green checkpoint, an audit. It is a closing habit stated once in the shared reference, not a new section in each skill.

  1. Today path: the reply is complete and correct, and still leaves the reader to supply the one thing the skill already knows — what to do next.
  2. After path: recommended first, and it is genuinely a recommendation — the skill just did the work and knows whether the plan is ready. Stopping stays a listed option, so the recommendation never becomes a push.
  3. After path: the exception keeps the habit from becoming noise. The test is whether control is actually returning to the user, not whether the reply happens to end a step.
