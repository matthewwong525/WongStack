What happens to one commit pushed to a branch that has an open pull request.

Today

Push one commit

The branch has an open pull request. GitHub fires two events for the same commit.

Details

Event 1: push. Event 2: pull_request (synchronize). Each event starts its own workflow run.

↓ Two events, no condition

push event

Payload checks runs. About 27 s.

Details

No job-level if. No concurrency group.

pull_request event

Payload checks runs again. About 27 s.

Details

The same commit, the same checks, a second runner. The result cannot differ from the push run.

↓ Both join here

Two runs per commit

About 54 s of runner time for one 27 s job.

Details

The Test and Deploy workflows already skip their pull_request run. Payload checks was added without that condition.

After

Push one commit

GitHub fires the same events as today. The workflow now decides which one runs.

Details

The triggers do not change. A job-level if and a concurrency group decide what happens next.

↓ Where does the commit come from?

Same-repo branch Changed

push runs the job. pull_request is skipped by the job-level condition.

Details

The condition passes when the event is push. The pull_request run shows as a grey "skipped" check. /save already reads a skipped Test or Deploy run as passing.

Fork pull request Kept

No push fires in this repo. pull_request still runs the job.

Details

The condition also passes when the head repository is not this repository. That is the only run a fork commit gets, so it must stay. The job has read-only permissions and no secrets.

↓ Both join here

One run per commit Changed1

One green run for the latest commit, and no run cancelled by the other event. The concurrency group keys on the event and the branch.

Details

Group name: payload-<event>-<branch>. Off the default branch, a newer commit cancels the older run in the same group. Two different events never share a group, so one cannot cancel the other.

See today

  1. github.ref differs between the two events, so a branch-only group never matches. A group that did match would cancel one run, and gh pr checks reads cancelled as fail.

.github/workflows/payload.yml — the top of the file. The group and the condition copy test.yml line for line. The header comment names test.yml as the owner of the explanation and does not repeat it. The steps below permissions do not change.

# Meta-only checks on WongStack's own payload. One run per commit:# see "Why one commit does not test twice" in .github/workflows/test.yml.name: Payload checkson:  push:  pull_request:concurrency:  group: payload-${{ github.event_name }}- 1    ${{ github.head_ref || github.ref_name }}  cancel-in-progress: ${{ github.ref_name != github.event.repository.default_branch }}jobs:  payload:    if: ${{ github.event_name == 'push' || 2      github.event.pull_request.head.repo.full_name != github.repository }}    runs-on: ubuntu-latest    permissions:      contents: read    steps:      # unchanged
  1. The group key includes the event name. github.ref differs between push and pull_request, so a branch-only key never matches, and a key that did match would let one event cancel the other. cancel-in-progress is off on the default branch, so a merge is never cancelled by the next merge.
  2. The condition keeps pull_request only for fork pull requests. A fork fires no push here, so that run is the only check a fork commit gets. A same-repo pull request is already covered by its push run.
