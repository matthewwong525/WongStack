# Each finished plan is kept as one file, so Paseo stops lagging

**Status:** ready-to-ship
**Branch:** groovy-bear
**Open questions:** none

## Why

Paseo watches each repo's folders for changes, but only up to 5,000 folders. Past that, it falls back to checking again and again, and every chat on that repo lags and drops its connection. Finished plans cause it: each one keeps its own folder, plus a folder for each part. ClaymooApp has 1,245 finished plans in about 4,400 folders, 5,600 in all. WongStack has 455 finished plans in 1,904 of its 2,179 folders, so it is on the same path.

## What Changes

- **Each finished plan becomes one readable file.** You can still search it, open it on GitHub, and see its history. Every part is kept exactly, word for word: the plan, its specs, its tasks, its review page, and its pictures. The pictures go inside as encoded text.
  ```text
  Before                      After
  archive/                    archive/
    2026-11-17-wiki-folder…/    2026-11-17-wiki-folder….md
      proposal.md               2026-11-16-…md
      design.md                 …
      tasks.md
      review.html
      specs/company-knowledge/
        spec.md
    … 454 more folders
  ```

- **Shipping a plan packs it at once.** `/ship` finishes the plan as it does today, then packs its folder into one file before saving. The OpenSpec tool keeps working: it never reads finished plans, and a test on a copy of this repo showed that listing plans, checking specs, and finishing a new plan all still work.
  ```mermaid
  flowchart LR
    A["Plan finished"] --> B["Packed to one file"]
    B --> C["Saved"]
  ```

- **Everything that reads finished plans reads the packed file.** Memory search, `pull`, the review page builder, the "other work" check, the save and ship steps, and the daily tidy find a finished plan as before. An old link to a file inside a finished plan, in a memory fact or a page, still finds that file.

- **An old review page still opens.** Asked for a finished plan's review page, the builder unpacks that plan to a scratch folder and prints the page's address there, with its screens and pictures beside it.

- **WongStack packs its own 455 finished plans in this change.** Its folders go from 2,179 to about 70.

- **Other repos pack theirs at their next update.** The update plan gets one to-do that packs every finished plan in one go, then checks each file opens back to the same content. ClaymooApp goes from about 5,600 folders to about 1,200.

## What the build needs

- **Nothing.**

## Non-goals

- Plans still in progress keep their folders: the OpenSpec tool reads and writes them.
- No change to what a finished plan says: packing changes only how it is stored.

# Design

## Context

Paseo's file watcher stops watching a repo past 5,000 folders and polls instead, which makes every chat on it lag. `openspec/changes/archive/` holds 1,904 of this repo's 2,179 folders and about 4,400 of ClaymooApp's 5,600. Every archived change is a folder, `specs/<cap>/` folders, and sometimes `prototypes/`, `pictures/`, or evidence folders.

The OpenSpec CLI (1.13.2) never reads `archive/`: `list`, `view`, and `archive` skip it, and `archive` only writes `archive/<date>-<name>/` and fails if that folder exists. A test on a copy of this repo with every archive packed passed `openspec list`, `validate --specs --strict`, and `archive demo` (folders 2,179 → 68).

About 14 scripts read archive folders directly (listed in the proposal's Impact).

## Goals / Non-Goals

**Goals:** one file per archived change; byte-exact round trip; every reader works on the packed form; this repo migrated; installs migrated by their next update.

**Non-Goals:** packing active changes; changing the OpenSpec CLI; compressing; rewriting archived content.

## Decisions

### The packed format

`openspec/changes/archive/<date>-<name>.md`, UTF-8 text, length-prefixed so content can never be mistaken for a marker:

```text
<!-- openspec-archive v1 2026-11-17-wiki-folder-per-chat -->
<!-- file proposal.md utf8 1834 -->
…exactly 1834 bytes…
<!-- end proposal.md -->
<!-- file review.html utf8 48211 fence=~~~~ -->
~~~~html
…exactly 48211 bytes…
~~~~
<!-- end review.html -->
<!-- file pictures/a.png base64 20480 -->
…one base64 line of 20480 characters…
<!-- end pictures/a.png -->
```

- The byte count is the parser's truth; the `end` line is checked as a guard. A count that does not land on its `end` line is a corrupt file and fails loudly.
- Order: `proposal.md`, `design.md`, `tasks.md`, `specs/**` sorted, then every other file sorted. Markdown files go in raw, so GitHub renders the plan as one readable page (comments are hidden).
- Other text files (html, yaml, json, css) sit inside a tilde fence outside the counted bytes, longer than any tilde run in the file, so GitHub shows them as code and not as live HTML.
- A file that is not valid UTF-8, or holds a NUL byte, is `base64` on one line. Empty folders (`.gitkeep` only) keep the `.gitkeep` entry.
- Alternatives: a zip (rejected by the owner: not searchable or readable on GitHub); flattened file names with no folders (keeps ~3,400 files and is not "one file").

### One owner: `.agents/plugins/loop/scripts/archive.mjs`

Exports `pack(folder)`, `unpack(file, dir)`, `listArchived(root)` → `[{ folder, name, file, packed }]` (packed files and any leftover folders, newest first), `readArchived(root, folder, path)` → text or null, `filesOf(root, folder)`, and `resolveArchivePath(root, path)` for `openspec/changes/archive/<folder>/<file>`. CLI: `archive.mjs pack <folder>…`, `archive.mjs unpack <name> [--to <dir>]`, `archive.mjs migrate [--root <dir>]` (packs every leftover folder: pack, unpack to a temp dir, compare every file's hash, then delete the folder; a mismatch keeps the folder and exits 1), `archive.mjs check` (every packed file parses).

Readers accept both forms, so a half-migrated repo, or a branch that predates the migration, still reads.

### Readers

- **Loop module:** `ship.mjs` runs `pack` on the change's archive folder after `markReady`, and `archiveFolders` matches `<date>-<name>.md` too, so a rerun finds an already packed change. `checkpoint-evidence.mjs` and `other-work.mjs` treat `openspec/changes/archive/<folder>.md` as the archived change `<folder>` (proposal read from the packed file through `git show`). `render-pr-body.mjs` strips the `.md`. `build-review.mjs` on a packed path or an archived name unpacks to `.scratch/archive/<folder>/` and prints that page; it never writes into the archive.
- **Memory:** `.agents/memory/profile.mjs` gains `archive: { list, read }`, lazily from the loop's `archive.mjs`. The memory module's `pull.mjs` (`archivedFolder`, `proposalOf`), `corpus.mjs` (lists packed files and expands each into its proposal, design, tasks, and spec entries at their old virtual paths; `safeSource` resolves those through the slot), and `daily-tidy.mjs` (`existsIn`) use the slot, and treat an empty slot as no archived changes. `.agents/memory/lookup.mjs` (`slugState`, `changePaths`, `lookupLines`) and `lib/links.mjs` (skip `archive/*.md` as it skips the folder) use `archive.mjs` directly.

### Migration

- **This repo:** run `archive.mjs migrate` in the change; commit the 455 new files and the removed folders.
- **Installs:** `preflight.mjs` reports catch-up reason `unpacked-archive` when `openspec/changes/archive/` holds any change folder; `catch-up.md` adds the step: run `archive.mjs migrate` in the build, before publish, and name the count in the plan. The CHANGELOG entry's **Updating.** note says it in plain words.
- An old branch merged after the migration may bring a folder back (as fact #41 describes for active changes); `migrate` is safe to rerun, and `/ship` packs its own change.

## Risks / Trade-offs

- **One huge diff.** The migration commit removes ~3,400 files and adds 455. `git log --follow` on an old archive file stops at the migration; `git log -- <folder>` before it still works.
- **Large text files.** Packed files carry review pages (29 MB total) and pictures as base64 (~6.4 MB → ~8.5 MB). Search tools that read the whole repo read them as text; `corpus.mjs` indexes only the plan parts, and the size cap per file applies per part, not per packed file.
- **Corrupt or hand-edited packed file.** The length check fails loudly and names the file; `archive.mjs check` runs in the payload checks.
- **The CLI might start reading `archive/` in a later version.** The CLI contract page notes the packed form; an update that changes the CLI re-runs the copy test.

## ADDED Requirements

### Requirement: A finished change is kept as one file

A shipped change SHALL be stored under `openspec/changes/archive/` as one readable text file, not a folder. The file SHALL hold every file the change's folder held, each restored byte for byte, so no folder is added per finished change. Every WongStack step that reads a finished change SHALL read the packed file, and the old path to a file inside a finished change SHALL still find that file.

#### Scenario: Shipping a change packs it

- **WHEN** `/ship` archives a change
- **THEN** the saved archive holds one file for that change and no folder
- **AND** the OpenSpec CLI still lists, validates, and archives other changes

#### Scenario: An old path still finds its file

- **WHEN** a memory fact or a page names a file inside a finished change by its old folder path
- **THEN** memory, the review page builder, and the other WongStack steps find that file in the packed file

### Requirement: An update packs an older install's finished changes

An update of an install whose archive still holds change folders SHALL plan one step that packs every one of them. The step SHALL check that each packed file restores the same files before it removes a folder, and it SHALL keep a folder it can not restore exactly.

#### Scenario: ClaymooApp updates

- **WHEN** an install with 1,245 archived change folders updates
- **THEN** its sync plan has one step that packs them, and after the update its archive holds no change folder

      f = Math.min(1, (row - 110 * small.length) / Math.max(1, rest.reduce(function (t, s) { return t + s.w * s.k; }, 0)));

      if (!more.length) break;
      small = small.concat(more);

      // A gone file keeps the buttons, as a 429 does: the person picks it again and taps once more.
      if (line !== GONE) hideActions();
      says(line);
