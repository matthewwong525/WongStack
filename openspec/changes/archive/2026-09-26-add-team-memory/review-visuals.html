How each person reaches the memory store after this change. The admin and every teammate use the same path.

Everyone goes through the Worker

Admin Changed

Has an admin key for the repo.

Details

Actor: the admin. Action: runs memory.mjs. Result: the call goes to the Worker. The admin has no Cloudflare memory token now.

Teammate New

Has a member key for the repo.

Details

Actor: a teammate. Action: runs memory.mjs. Result: the call goes to the Worker. The admin made the key with member add.

↓ Both run the same script

A session calls the store Changed 1

CLOUDFLARE_MEMORY_TOKEN holds a memory key.

Details

Actor: memory.mjs. Action: sends the D1 query and R2 object calls with the key to the Worker URL in components.memory.worker. Result: one code path for all people.

↓

The wong-memory Worker New 2

One per Cloudflare account. Not part of any app.

Details

Actor: the shared memory Worker. Action: gets the calls of every repo in the account, home included. Result: it copies the two Cloudflare endpoints that memory.mjs already calls.

↓

The Worker checks the key New 3

It finds the key hash in the wong-memory-keys D1.

Details

Actor: the Worker. Action: hashes the key and looks it up. Result: the repo and the role, admin or member, and the email. Unknown key: 401. member remove deletes the row, so the key stops at once. Only the Worker binds this database.

↓ The key opens one repo's store

Repo A: memory D1 and bucket Open

The store that this key opens.

Details

Actor: the Worker. Action: runs the SQL and object calls through the repo A bindings. Result: facts for all; transcripts as the transcripts state shows.

Repo B (home): memory D1 and bucket 403 4

Bound to the Worker, but this key does not open it.

Details

Actor: a repo A key. Action: asks for the repo B store. Result: 403. Only a repo B key opens it.

App production D1 and app Workers Out of reach 5

The Worker has no binding to them.

Details

Actor: any key. Action: none is possible. Result: no memory key reaches the app's data or code.

Transcript access

A session uploads its transcript Changed 6

New key: sessions/<author email>/<agent>/<session-id>.jsonl.

Details

Actor: memory.mjs. Action: puts the email of the author in the key. Result: each transcript has an owner. Old keys, sessions/<agent>/<id>.jsonl, do not move.

↓ Who asks for the object?

Member, own email New

PUT and GET under sessions/<their email>/.

Details

Actor: the Worker. Action: compares the key prefix with the email of the member key. Result: allowed.

Member, other key New 7

Another person's key, or an old key with no email: 403.

Details

Actor: the Worker. Action: the prefix does not match. Result: 403. The object is not read or written.

Admin key Changed

Reads every key of its repo, old keys too.

Details

Actor: the Worker, for an admin key. Action: skips the prefix check in that repo's bucket. Result: all transcripts of the repo, including every sessions/<agent>/<id>.jsonl key.

  1. The .env name stays CLOUDFLARE_MEMORY_TOKEN, but it holds a memory key, not a Cloudflare token. Only the base URL changes, so the script keeps one code path.
  2. One shared Worker per account, not one per repo and not in the app. One per repo could mean hundreds of Workers. In the app, CI and every preview would get the memory bindings, and /wong-sync cannot update app/.
  3. Keys are stored as hashes in their own D1 database. No key's SQL can reach it, because only the Worker binds it. Worker secrets would cap the number of keys.
  4. One key opens one repo's store. Setup cannot read a key from another repo, because only hashes are stored.
  5. This is why the Worker exists: a Cloudflare token with D1 Write reaches every D1 database in the account. The Worker binds only memory databases and buckets.
  6. The email in the key is the only thing the Worker checks for transcripts. All transcripts of a repo stay in one bucket.
  7. Old transcripts have no email in their key, so they become the admin's. Members cannot read them.
