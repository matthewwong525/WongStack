# Cloudflare login-management contract

Verified against primary public API documentation on 2026-10-04. This records the source contract; it is not a live owner connection or propagation result.

- Update only the recorded application and human policy: `PUT /accounts/{account_id}/access/apps/{app_id}/policies/{policy_id}`. The documented accepted permission is `Access: Apps and Policies Write`. [Update policy](https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/applications/subresources/policies/methods/update/).
- Revoke sessions only for the recorded application: `POST /accounts/{account_id}/access/apps/{app_id}/revoke_tokens`. It revokes all application tokens. Either `Access: Apps and Policies Write` or `Access: Apps and Policies Revoke` is accepted. The policy-write credential therefore covers this endpoint without adding identity-provider, organization or provisioning authority. [Application revocation](https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/applications/methods/revoke_tokens/).
- Do not use organization-wide `revoke_user`; it affects unrelated applications and requires separate organization/identity-provider/group write authority.
- Provider scopes can cover the account rather than one application. Pin account/application/policy/Worker/origin/audience in private trusted state, and constrain the finite core adapter to those recorded resources. Independently read back their ownership, destination and policies before mutation; reject shared or unreviewed policies and preserve machine/verification rules. Do not reuse the deploy credential.
- The existing private setup keeps distinct exact-email human and verification policies. Read `.agents/skills/wong-setup/scripts/private-access.mjs` and `scripts/check-private-access.mjs` for compatibility, but this feature must not provision new apps, machine tokens or login providers.
- Revocation can require remaining teammates to sign in again. Local member denial, policy reconciliation and session/provider outcome are separate states; a success envelope alone does not establish observed propagation.
- Preserve durable desired generations/retries across lost responses, and converge an older external write to the latest desired generation. Never acknowledge an old job as the latest success or restore removed membership. Any in-flight request with an unknown outcome remains pending until safely reconciled.
- No production provider writes from staging. Controlled live readback/admission/session-denial proof remains task 6.3.

## Delivered reconciliation

Private operator setup separately verifies account-limited Access-only authority. The core seals it, validates recorded resources, rejects shared/unreviewed policies, preserves stricter controls and checks both controls and exact email readback. Connection verification leaves existing human policy untouched until the reviewed latch/database enforcement and explicit grants are enabled.

Policy PUT intents and pending work commit together before an external mutation. Lease/generation checks constrain fresh calls; stale responses converge current state. A crashed/lost older write stays durable and prevents a later matching removal readback from being called complete while the old write could still apply. Application-session revocation reports provider acceptance with propagation unverified. Owner retries drive independent outcomes; no scheduler or production provider writes are introduced in previews. Actual admission/removal propagation remains controlled acceptance, not source-fixture evidence.
