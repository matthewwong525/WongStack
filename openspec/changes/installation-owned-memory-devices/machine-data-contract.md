This is the task3.0c/3.0d source prerequisite. It installs no handler, caller, hook, CLI, setup adapter or provider resource. Schema12/13 SQL, manifests, original bootstrap pins and receipts remain unchanged. An exact source gate proves source checks only; it does not release a snapshot, live phase or ordinary memory access.

`trustedMachineDataContext` projects read-only actual Worker versions, immutable Worker IDs, resources, origins and critical bindings through the existing trusted inspector. A genuine public D1 context remains a separate capability and cannot inspect provider deployment state or invoke operator actions. Neither status reports ready.

`prepareMachineData` accepts `{operationId, expected, genesis}` on an exact completed13 installation. `expected` is the original four-field runtime snapshot. `genesis` is the exact `{pinHash,targetJson,evidence}` wrapper around independently inspected original deployment evidence. The separate14 manifest pins the exact SQL14 bytes. Compiled DDL validates every schema14 table/index/view/trigger body plus new fact/session/run columns; a receipt does not bless arbitrary readback DDL. SQL-only, partial, malformed, extra-table, mixed or future schemas are refused and never adopted on retry. A completed preparation retries only with its exact retained input.

An ordinary runtime snapshot keeps `{authRevision,pinRevision,runtimeRevision,snapshotHash}`. On validated14 the hash also binds data revision, maintenance barrier and deployment head. New data snapshots add `{dataRevision,deploymentHead}`. Existing13 reads fail closed during data maintenance; data attempts are excluded during13 authority, renewal or publication maintenance. Only branded internal data inspection or trusted inspection can read incomplete status, which remains blocked. No caller may bypass the barrier with a plain object.

## Capture

`captureMachineData` accepts `{attemptId,expected,payload,proof}`. The expected data snapshot is exact. Payload keys are:

- `machineId, repositoryId, grantId, machineCommitment, machineRevision, grantRevision, credentialGeneration, credentialHash`;
- `visibility` (`private` or `shared`) and `source` (`save`, `backfill` or `consolidation`; `migration` is refused);
- `newTags`: ordered `{name,definition,aliasOf}` definitions, with no overwrites; aliases refer to an existing or earlier defined tag;
- `session`: null or `{id,agent,status,reason,previousCursor,nextCursor,updatedAt,branch,cwd,startedAt,endedAt}`;
- `facts`: ordered `{slug,type,body,tags,supersedes}` entries, where supersedes holds exact fact IDs;
- `run`: null or `{startedAt,finishedAt,counts:{added,superseded,captured}}`, with server-verified exact tallies.

Owner and author always come from the authorized machine. No external owner, author, raw key, SQL or arbitrary object pointer is accepted. Reader capture is private; a reader's shared override refuses. User and feedback facts remain private in a mixed shared work capture. A session marked private has zero extracted facts/tag definitions. Private raw transcript disclosure never follows from a shared summary. Raw pointers remain in the separate13 immutable staged/published transcript ledger; later production code must derive the own object through exact session/content ownership, never accept `session.raw_key` from this capture request.

Fact IDs come from exact unique `(capture_attempt_id,capture_ordinal)` rows, never a global maximum. Each fact/tag/supersede outcome joins its own ordinal and owned row. Members supersede their own captured facts. Explicit data admins may append their own correcting fact superseding another captured owner in this installation/repository; the old owner's authored fields and ownership remain intact. Neither role adopts an unmapped legacy fact. Session cursor updates compare the previous cursor and record the attempt marker. An existing session from another machine cannot be claimed or updated. Session-only and run-only captures can complete with an exact empty fact outcome.

Proof uses a distinct `capture` P-256 purpose with the canonical `/_memory/v2/repositories/{repositoryId}/machines/{machineId}/capture` path, pinned origin, POST, attempt ID, exact ordered payload digest and expected digest. Schema13 proof purposes and bytes remain unchanged. The verified public JWK, nonce/proof hashes and deadline enter protected receipts; raw proof/credential values do not. Capture requires the latest completed, unexpired credential generation and live machine/grant revisions; persistent key possession cannot bypass ordinary renewal. Reused nonce across attempts is refused.

SQL independently verifies all durable facts, exact tags/definitions, owned supersedes, session metadata/cursor and run/tallies before outcome, audit and completion. Each stage rechecks live authority and proof deadline. A provider success envelope, zero-row statement or partial batch is insufficient. Incomplete attempts retain maintenance and are never replayed. Exact completed retries return their original receipt. Changed ordered payload conflicts. Rotation/revocation quarantines pending work; no acknowledgement restores authority.

Inputs are capped at100 facts,30 tags per fact,100 supersedes per fact,30 definitions,64 KiB serialized payload and200 planned write statements. Oversize inputs refuse with `capture-payload-too-large` before an attempt/barrier. These source limits are not a free-tier or live D1 guarantee: the later route/client gate must include every validation/read/write query in its invocation budget and chunk ordinary captures accordingly.

`readSignedMachineDataStatus` uses a separate fresh `capture-status` proof frame and `{machineId,grantId,machineCommitment,targetAttemptId,requestHash}` payload. It returns only that active machine/grant's exact retained completed outcome and current data snapshot, marked `access: receipt-only`. Old snapshot/proof lifetime and bearer rotation/expiry do not erase the receipt. A fresh status proof is still required; revoked/removed machines, wrong grant/key/purpose, foreign receipts and partial outcomes deny. When the target ID is genuinely absent, the fresh same active machine/grant proof returns only sanitized `absent: true` plus the current own snapshot. An existing wrong-hash, foreign or incomplete attempt refuses; it is never projected as absent. A later client may create a NEW attempt containing identical notes bound to this same machine/grant, never resume partial work or rebind it to replacement authority. This function replays no mutation and grants no bearer/data access or directory listing.

## Deployment successors

`recordMachineDeployment` is trusted only. Input `{attemptId,expected,payload}` binds `{predecessorId,previousPinHash,pinHash,evidence,reviewHash,protocolHash,routeContractHash,rollback}`. The actual normalized evidence must independently equal the exact reviewed input, and its review hash must match. The original genesis and every completed predecessor are retained and validated. The predecessor need not still serve traffic: the new actual deployed version is inspected directly. A stale, unknown or competing predecessor refuses; a partial successor keeps the store closed. Lost responses recover the exact completed successor without repinning or replaying writes.

A rollback is another explicit reviewed successor. It preserves original12/13 pin history, tombstones, authored data and completed receipts. It never resets/adopts an old store or reopens revoked authority. Exact immutable Worker/resource/origin IDs remain pinned while reviewed actual version/critical-binding evidence is appended.

Compiled protocol and route hashes describe supported source shapes. They never assert that a provider deployed those bytes. Public D1 alone cannot observe an unreviewed provider redeploy; its source status remains pending. The later strict production route gate must compare the actual executing `CF_VERSION_METADATA.id` against the completed successor's exact version and compare compiled activation hashes, so retained/unreviewed versions deny even at the canonical origin. The schema14 base compiled pair stays supported forever. The planned separate full-core gate records its exact public protocol/complete allowlist hashes in the existing immutable schema13 activation during fresh trusted setup, before machine grant activation. Schema14 successors continue acknowledging the retained base14 capability and exact executing version; normal business redeploy keeps the full-core hashes stable. An already activated13 installation with an unsupported activation pair refuses unchanged until an explicit reviewed compatibility path exists. Neither activation nor old receipts may be reset/relabelled to claim readiness. This full-core contract is planned and is not implemented or callable by this source slice. No config binding or public route is added here.
