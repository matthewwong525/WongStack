Where a memory call goes, today (21.0.0) and after this change, and how memory ships.

After

memory.mjs sends a memory call

A member or the admin, with a memory key (wongm_...).

Details

Actor: memory.mjs. Action: send the D1 query or R2 request to the recorded URL, https://<worker>.<subdomain>.workers.dev/_memory. Result: the request reaches the repo's own app Worker.

↓ Which Worker answers?

Production Worker <repo> Changed 1

/_memory/* goes to the memory module. All other paths go to the app.

Details

Actor: the app Worker. Action: check the key hash, then run the call on its bindings. Bindings: DB (the app), MEMORY_DB, and MEMORY_BUCKET. Result: the same endpoints and shapes as 21.0.0.

Staging Worker and previews Changed 2

No memory bindings. /_memory/* answers 404.

Details

Actor: the staging Worker or a preview. Action: none for memory. Result: HTTP 404. A branch cannot read or write memory.

↓ Production only

The repo's memory store Changed 3

The memory database, with a memory_keys table inside it, and the bucket.

Details

Actor: the memory module. Action: refuse every statement that names memory_keys or writable_schema. Result: no key can read or change keys. A key from another repo is not in this table, so it gets HTTP 401.

See how memory ships

Today (21.0.0)

memory.mjs sends a memory call

With a memory key, to the account's shared Worker.

Details

Actor: memory.mjs. Action: send the call to the wong-memory URL. Result: the call does not touch the repo's app Worker.

↓

Shared Worker wong-memory, one per account

Binds every repo's memory database and bucket, and KEYS.

Details

Actor: the shared Worker. Action: find the binding for the database id or bucket name in the path. Result: the binding list grows with each repo, and a person deploys it with memory.mjs worker deploy.

↓

Each repo's memory store

A memory database and a bucket for each repo.

Details

Actor: the shared Worker. Action: run the call on the matched binding. Result: one Worker serves many stores.

wong-memory-keys database

The key hashes for all repos. One more D1 database.

Details

Actor: the shared Worker. Action: check the key hash. Result: no request path reaches this database.

↓ Separate from memory

App Worker <repo>

Serves the app only. CI deploys it.

Details

Actor: CI. Action: deploy the app on each push. Result: the app and memory are two things to deploy and manage.

How memory ships

A push to GitHub

A memory change is app code now.

Details

Actor: a person or /save. Action: push a commit. Result: deploy.yml runs cf-build.sh and cf-deploy.sh.

↓ Which branch?

Merge to main Changed 4

CI deploys the production Worker with MEMORY_DB and MEMORY_BUCKET.

Details

Actor: CI, with the deploy token. Action: wrangler deploy from app/wrangler.jsonc. Result: the memory route goes live. The token needs Workers R2 Storage Write when the store has a bucket.

Any other branch

CI deploys the staging Worker and a preview, with no memory bindings.

Details

Actor: CI. Action: wrangler deploy --env staging, then a preview upload. Result: /_memory/* answers 404 there. CI never migrates the memory database as the app's.

↓ Not through the Worker

Admin commands go straight to Cloudflare Changed 5

member add, member remove, member list.

Details

Actor: the admin. Action: run the command with CLOUDFLARE_API_TOKEN. Result: it writes memory_keys through the Cloudflare D1 REST API. No person runs a memory deploy; memory.mjs worker deploy is removed.

  1. Memory moves into the app Worker that every install already has. Per account, one Worker and one D1 database are fewer. The risk: a failed production deploy also stops memory, and app code can reach the memory bindings.
  2. Only production gets the bindings, so a branch or preview cannot read transcripts. The 404 also makes a new install spool its facts until the first production deploy.
  3. The keys table sits in the memory database because a separate keys database per repo costs one of the free plan's 10 D1 databases. The Worker ignores the database id and bucket name in the path, because it serves one store.
  4. The bindings come from the stack pack's wrangler.jsonc fragment, in production only. secrets:check does not ask staging for a MEMORY_* twin.
  5. Key management never passes through the Worker, so no memory key, not even the admin's, can change keys.
